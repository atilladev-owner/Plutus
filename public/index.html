What it is

A ledger you can audit and an exchange you can trade against.

Plutus is a multi asset ledger, and from milestone two a paper trading exchange, built as a single HTTP API. Mint a key with no signup, open a ledger, and move money between accounts under invariants the database enforces itself rather than application code that might forget to check them.

Every amount is an integer count of the asset's smallest unit, never a float. Every write, a transfer, a hold, a capture, an order fill, runs as one Postgres function under row locks, so two requests racing for the same balance or the same market cannot both win. Every write also appends to a hash chained journal, so one request can prove the whole history is intact, not only the balances it left behind.

The exchange is built entirely on top of the ledger, not beside it. A fill is a ledger transfer with three legs. The exchange cannot create or destroy money, and its own verify endpoint proves that on demand.

How it works

The ledger

A ledger holds one or more accounts, each denominated in one asset. A transfer moves money between accounts as a list of legs, all committed together or not at all. Balances only ever change through a transfer, so there is never a code path that edits a balance directly and skips the record of why.

Holds

A hold reserves funds against an account without moving them yet. It is captured, for the amount actually owed, or released back to the account it came from. An exchange order uses a hold the same way: placing a limit buy holds the money it might spend, and a fill draws from that hold rather than the account directly.

Journal and chain

Every write appends one entry to that ledger's journal, and every entry carries the hash of the entry before it. Tamper with one entry, even a value nobody reads day to day, and every entry after it fails to recompute. The verify endpoint walks the whole chain and reports the first place it breaks, not just whether today's balances look right.

Matching

An order for a market takes that market's own lock before anything else happens to it, so two orders on the same market are always resolved one at a time, never as a race. The book is walked in price time priority: the best resting price fills first, then the next, until the incoming order is filled or nothing better is left to trade against. Every fill posts one ledger transfer, three legs: the quote asset to the seller, a fee to the house, and the base asset to the buyer.

The house

The house is an ordinary key with ordinary balances, not a hidden privileged account. It quotes a ladder of five bids and five asks around the current reference price only when a request actually looks at the market, and lets that ladder go stale otherwise. There is no background loop pretending to be a market that never sleeps.

What to build with it

The ledger's primitives, accounts, transfers and holds, are general enough to carry patterns well outside trading. Four worth naming:

Savings groups

A rotating group savings circle: one ledger per group, one account per member. Contributions are transfers from a member's account into a shared pot; a payout on schedule is a transfer back out. The group's own history is the journal, not a spreadsheet someone has to keep honest.

Group expenses

Shared costs between people who trust each other but still want a record: an account per person, an expense recorded as a transfer between whoever paid and whoever owes their share. Who owes what is a balance read, not a reconciliation someone runs at the end of the trip.

Tabs

A running tab at a bar or a café: open it with a hold against the customer's account for a sensible ceiling, capture the exact amount owed when they settle up, release the rest. Nobody's money moves until the tab actually closes.

Deposits

A booking or a rental deposit: a hold placed at the time of booking, captured in full or in part if something was owed against it, released back untouched if it never was. The hold's own state is the answer to whether a deposit is still outstanding.

Set it up

Mint a key

No signup. A sandbox key comes back from one call, ready to use immediately.

curl -s -X POST https://plutus-ten-eta.vercel.app/v1/keys

The first three calls

Thirty seconds

# 1. a key, no signup
curl -s -X POST https://plutus-ten-eta.vercel.app/v1/keys
# 2. a ledger and two accounts
curl -s -X POST https://plutus-ten-eta.vercel.app/v1/ledgers -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"name":"shop"}'
curl -s -X POST https://plutus-ten-eta.vercel.app/v1/ledgers/$LEDGER/accounts -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d '{"asset":"GHS","name":"till"}'
# 3. money in from the world, then between accounts
curl -s -X POST https://plutus-ten-eta.vercel.app/v1/ledgers/$LEDGER/transfers -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -H "Idempotency-Key: fund-1" -d '{"legs":[{"from":"world:GHS","to":"'$TILL'","asset":"GHS","amount":"125000"}]}'
# 4. prove the books
curl -s https://plutus-ten-eta.vercel.app/v1/ledgers/$LEDGER/verify -H "Authorization: Bearer $KEY"

Signing for trading

Exchange trading endpoints sign every request instead of sending a bearer token. Four headers travel together: X-Plutus-Key-Id, X-Plutus-Timestamp in Unix milliseconds, X-Plutus-Recv-Window in milliseconds, and X-Plutus-Signature, a hex HMAC SHA256 over timestamp + "\n" + METHOD + "\n" + path + "\n" + body, keyed by the SHA-256 digest of the key secret rather than the secret itself, since that digest is all the server ever stores. The worked example below uses a key id and secret invented for this page, so the signature can actually be recomputed rather than taken on trust.

Key id: key_4f9a2c7e1b3d4a5f8e6c9b0a1d2e3f4a. Secret: pl_test_4f9a2c7e1b3d4a5f8e6c9b0a1d2e3f4a5b6c7d8e9f0a1b2c. This key does not exist. Signing with it authenticates against nothing, live or otherwise. The exact bytes HMAC SHA256 signs, keyed by the SHA-256 digest of that secret, one line for the timestamp, the method, the path and the body, with no trailing newline after the body:

1767225600000
POST
/v1/exchange/orders
{"market":"BTC-USDT","side":"buy","type":"limit","price":"6000000000","quantity":"100000"}

signRequest (src/platform/signing.ts) is what actually produced the header below from those bytes and that secret.

BODY='{"market":"BTC-USDT","side":"buy","type":"limit","price":"6000000000","quantity":"100000"}'
curl -s -X POST https://plutus-ten-eta.vercel.app/v1/exchange/orders \
  -H "Content-Type: application/json" \
  -H "X-Plutus-Key-Id: key_4f9a2c7e1b3d4a5f8e6c9b0a1d2e3f4a" \
  -H "X-Plutus-Timestamp: 1767225600000" \
  -H "X-Plutus-Recv-Window: 5000" \
  -H "X-Plutus-Signature: 16b66c8f8680c4b9c8208e70f9abafa7821eeb9eafa3dba686fe0b4f9a0dbbbc" \
  -d "$BODY"

docs/place-order.mjs in the repository reimplements this with nothing but node:crypto, reads a key id and secret from the environment, and places one real order against the live host from any machine, including one that has never cloned this repository.

The faucet

A sandbox key funds itself from the world with 100,000 USDT, 1 BTC and 10 ETH, once per 24 hours. It is a signed call like any other trading endpoint, using the same example secret shown above. Its own signed bytes:

Verify it

Two endpoints let a stranger check the books without taking anyone's word for it.

A ledger you own

GET /v1/ledgers/{id}/verify, with your key, recomputes that ledger's whole hash chain from the first entry and confirms every asset it holds still sums to zero.

curl -s https://plutus-ten-eta.vercel.app/v1/ledgers/$LEDGER/verify -H "Authorization: Bearer $KEY"

The exchange, with no key at all

GET /v1/exchange/verify takes no key and runs the same proof against the exchange's own ledger, so anyone can confirm the exchange has never created or destroyed money, without ever holding a key of their own. Limited to 2 requests per minute per address.

curl -s https://plutus-ten-eta.vercel.app/v1/exchange/verify
