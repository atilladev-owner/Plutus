Limits and proof

Every ceiling the sandbox and the exchange enforce, the ten named reasons an order is rejected, and two live checks: one reading the exchange's own proof right now, one showing what running the same proof against a ledger looks like.

Sandbox ceilings

Ceilings apply to sandbox keys and their ledgers. A ceiling hit is a 409 named sandbox_limit_reached, naming the ceiling. The exchange ledger and the house key are system owned and exempt.

CeilingValue
Ledgers per key10
Accounts per ledger50
Journal entries per ledger10,000
Webhook endpoints per key5
Open holds per account100
Request body64 KB
Metadata20 keys, 500 character values
Idle sandbox ledgerdeleted after 14 days without a write
Idle sandbox keydeleted after 30 days without a request, with its ledgers

Exchange ceilings

Every response carries RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset. A refusal is a 429 named rate_limited with Retry-After in seconds.

CeilingValue
Endpoint weight1,200 per minute per key
Order placement10 per second per key
Faucetonce per 24 hours per sandbox key
Markets listfree, no weight, cached 2 seconds
Book, trades, ticker5 each, per address, cached 2 seconds
Candles10, per address, cached 2 seconds
Stream opens12 per minute per address
Concurrent streams10 per address
Public exchange verify2 per minute per address

The ten rejection reasons

A rejected order still gets an id and a stable reason, never a bare error. Every one is named order_rejected.

ReasonMeaning
market_haltedthe market is not accepting orders right now
price_not_tickthe price is not a multiple of the market's tick size
quantity_not_lotthe quantity is not a multiple of the market's lot size
below_min_notionalprice times quantity falls under the market's minimum
insufficient_fundsthe hold this order needs cannot be covered
post_only_would_takea post only order would have filled immediately
fok_not_fillablea fill or kill order could not fill in full
duplicate_client_order_idthis key already used that client order id with a different order
self_tradethis order would fill against the same key's own resting order
notional_too_largeprice times quantity does not fit back into the exchange's integer arithmetic

Two live checks

The exchange lives in one system ledger anyone can verify without a key. A ledger you open yourself needs your own key to read, so its panel shows how to run the same proof rather than running it for you.

The exchange, right now

Waiting for JavaScript

Needs JavaScript enabled.

Read once per page load from GET /v1/exchange/verify, no key needed. A 429 here reads as checked recently, since this public route is limited to two reads a minute per address, not as a failure.

A ledger you own

Run with the key that owns it. Recomputes the whole hash chain from the first entry, replays every balance and held amount, and sums each asset.

curl -s \
  https://plutus-ten-eta.vercel.app/v1/ledgers/$LEDGER/verify \
  -H "Authorization: Bearer $KEY"

The document shape, the same one the exchange panel reads:

{
  "ok": true,
  "entries_checked": 1042,
  "first_bad_seq": null,
  "chain_ok": true,
  "sequence_ok": true,
  "replay_matches": true,
  "assets": [
    { "asset": "GHS", "sum": "0" },
    { "asset": "USDT", "sum": "0" }
  ],
  "cached": false
}
